# Study guide: explain it yourself (Days 11-20)

The pass rule: _"explain your own code and tests without reading an AI answer."_ Cover the answers, say yours aloud, then check. Short key points only.

| Day | Question                                                                      | Key points                                                                                                                                                                   |
| --- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 11  | Why is "Allowed files: ONLY" in a task brief?                                 | Stops the agent "helping" by refactoring unrelated code it saw; makes the diff reviewable. Note: it conflicted with "add a test", so the test file had to be allowed too.    |
| 11  | What does the diff review check?                                              | Allowed files, non-goals, acceptance checks, no unrelated edits.                                                                                                             |
| 12  | Name the three risk vectors in the review brief and one finding for each.     | Authorization bypass (client-chosen user id), data leakage (`SELECT *` returned password hashes), missing unhappy-path tests (only a happy-path test).                       |
| 12  | Why was the review brief "bounded"?                                           | Role, input, vectors, output format and a "no style comments" rule keep findings concrete and testable.                                                                      |
| 13  | What did you cut from the 1,177-word prompt and what must never be cut?       | Cut history, pleas, flattery. Never cut acceptance criteria and non-goals (checked by 13 criteria patterns + a negative control).                                            |
| 14  | What does a component test prove that a browser test misses, and the reverse? | Component: exact contract (URL, header, no client user id). Browser: real wiring, 401 handling, bundle and server. Measured: 4/6 vs 5/6 planted bugs, 6/6 together.          |
| 14  | Why are `toBeDefined()` tests weak?                                           | They pass on broken code (0/6 caught).                                                                                                                                       |
| 15  | Why is hiding a Delete button not authorization?                              | The attacker never uses the UI; they send `DELETE` directly. The server must check ownership on every request. Demonstrated: 200 on the insecure API, 404 on the secure one. |
| 15  | Which OWASP edition did you use and what was not covered?                     | Top 10:2025. A03 checked via `npm audit` (dev-only advisories accepted); A08 not demonstrated or tested.                                                                     |
| 16  | Name the five minimum AI-COO inputs.                                          | Approved objective; named human owner and reviewer; allowed repos and environment; acceptance criteria and non-goals; permission bounds (Read/Write/Merge).                  |
| 16  | Why can an agent never have merge permission?                                 | Merging is a human approval; otherwise it is an autopilot (handbook). Enforced by `NO_AGENT_MERGE`.                                                                          |
| 17  | What does the lifecycle enforce?                                              | Human gates, no skipped steps, no self-review, same SHA everywhere, "Not Run is not Passed", a new commit invalidates review and CI.                                         |
| 18  | What may a handoff report contain?                                            | Only PR link, final SHA, scoped objective, test evidence, remaining blockers. No code, no secrets (validator enforces it).                                                   |
| 18  | Which safety controls could you not verify locally?                           | Branch protection, GitHub secret scanning, token scopes, audit log: reported `MANUAL`.                                                                                       |
| 19  | Why does the server re-validate?                                              | The client is untrusted; client checks are UX.                                                                                                                               |
| 19  | Walk through one validation rule and its edge cases.                          | e.g. 30 days: 30 is OK, 31 fails; same-day is 1 day; leap day 2028-02-29 is valid, 2026-02-29 is not; overlap is inclusive.                                                  |
| 20  | What bug did your review find that tests missed, and why did they miss it?    | Stale server error after fixing the other date. No test covered that transition; mutation checks only catch bugs you plant.                                                  |
| 20  | Why "Final Candidate Rule"?                                                   | Any new commit invalidates earlier evidence; re-run everything on the final SHA.                                                                                             |
