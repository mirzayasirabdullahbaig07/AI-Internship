**Target:** `lab/insecure/notesApi.js` (an intentionally insecure Node.js notes API: login, list, create, delete).
**Standard:** OWASP Top 10:**2025** (A01-A10, published November 2025 - source: owasp.org/Top10/2025).
**Line numbers** refer to `lab/insecure/notesApi.js`. "Proven by" names a real test in `tests/security.test.js` that **fails** on the insecure code (`npm run test:insecure`) and **passes** on the secure code.

## A03 in detail: real `npm audit` result (`evidence/npm_audit.txt`)

- Runtime dependencies: **none** (`dependencies: {}`), `npm audit --omit=dev` -> **0 vulnerabilities**.
- All dependencies: **19 moderate** findings, all one advisory chain in dev-only test tooling (`sprintf-js` -> `argparse` -> `js-yaml` -> Jest's coverage plugin). The suggested fix (`npm audit fix --force`) installs `babel-jest@25`, a **breaking downgrade**, so I did **not** apply it. Decision: accepted as dev-only risk and recorded; revisit when Jest ships an updated dependency.

## Check: why hiding a "Delete" button in the frontend HTML is not authorization

HTML, CSS and JavaScript run on the **user's** machine, so they are suggestions the user can change. A hidden or disabled button can be un-hidden in DevTools in seconds - and the attacker never needs the button at all, because the button is only a way to send an HTTP request. They can send `DELETE /api/notes/1` directly with `curl`, `fetch` or Postman, and the server will do whatever _it_ decides.

**Authorization must be enforced on the server, on every request, using the verified identity and the resource's owner.** Hiding the button is good UX (do not show actions that will fail); it is not a security control.

**Proof (live demo, real servers):** the page hides the Delete button because the note is not Ayesha's. A direct request to the insecure API still returns `200 {"deleted":true}` and Yasir's note is gone. The same request to the secure API returns `404` and the note survives.
